# Реєстр ризиків проєкту (Project Risk Register)

## Проєкт: Beer Tracker Backend API
**Контекст:** Specification-Driven Development (SDD) із використанням AI Coding Assistant (Antigravity)  
**Ревізія специфікації:** SRS v2.1.0  
**Дата актуалізації:** 2026-10-12  

---

## 1. Методологія оцінки ризиків

Кожен ризик оцінюється за двома параметрами за шкалою від 1 до 5:
- **Ймовірність (Probability, $P$):** 1 (дуже низька) — 5 (майже неминуча).
- **Вплив (Impact, $I$):** 1 (незначний) — 5 (катастрофічний).
- **Критичність (Risk Score, $R = P \times I$):**
  - **Низька (1–6):** Моніторинг у робочому порядку.
  - **Середня (8–12):** Необхідні превентивні заходи.
  - **Висока (15–25):** Обов'язкове блокування та контроль через Quality Gate.

## 3. Детальний аналіз специфічних ризиків ШІ-конвеєра

### RSK-AI-01: Неправильне тлумачення вимог (Prompt Drift & Hallucination)
- **Прояв:** Агент додумує функціональність, відсутню в SRS (наприклад, розрахунок проміле BAC, соціальні лайки, геодані), або трактує вимогу з відхиленням від семантики (наприклад, повертає `400` замість `422`).
- **Можливі наслідки:** Роздування обсягу проєкту (Scope Creep), порушення контракту зовнішнього API, невідповідність стандарту IEEE 830.
- **Спосіб виявлення:** Звірка генерованих інтерфейсів із матрицею простежуваності; наявність невідомих маршрутів в API; інспекція під час PLAN-GATE.
- **Захід з попередження/пом'якшення:** Правило суворої простежуваності (Zero Hallucination); кожна дія агента прив'язується до стабільного `REQ-ID`. Будь-яке розширення відхиляється людиною.

### RSK-AI-02: Недетермінованість результатів (Stochastic Generation)
- **Прояв:** При повторних запитах на реалізацію або рефакторинг агент генерує різну структуру класів, використовує змінні конфігураційні стилі або нестабільні сигнатури методів.
- **Можливі наслідки:** Несумісність модулів між ітераціями розробки, нестабільність тестових запусків.
- **Спосіб виявлення:** Запуск лінтерів, Checkstyle/Spotless, перевірка структури пакетів проти заздалегідь визначеної архітектури.
- **Захід з попередження/пом'якшення:** Фіксація базових доменних класів (наприклад, `BeerEntity.java`) та єдиної конфігурації компілятора в `pom.xml`.

### RSK-AI-03: Кореляція помилок між кодом і тестами (Circular Validation Bias / Sycophancy)
- **Прояв:** Агент, отримавши завдання написати і тест, і код, генерує тест, який перевіряє не бізнес-правило специфікації, а специфічну помилкову поведінку власного коду (наприклад, перевірка хибної формули чи толерантність до відсутності транзакції). Тест проходить успішно ("зелений"), але вимога SRS не виконана.
- **Можливі наслідки:** Фальшиве відчуття 100% тестового покриття при наявності критичних архітектурних дірок.
- **Спосіб виявлення:** Інспекція assert-умов тесту людиною; крос-перевірка BDD-сценаріїв за файлом `spec/acceptance_criteria_bdd.md`; мутаційне тестування (Pitest).
- **Захід з попередження/пом'якшення:** Сувора TDD-дисципліна з двох окремих кроків: спочатку створюється задача `type:test` за текстовою специфікацією, фіксується статус RED, і лише після цього запускається генерація виробничого коду. Тести обов'язково рецензуються інженером (Human Code Review).

### RSK-AI-04: Втрата або застарівання контексту (Context Window Degradation)
- **Прояв:** У процесі тривалої розмови агент "забуває" архітектурні обмеження, узгоджені на початку сесії (наприклад, незмінність журналу, використання Testcontainers, або специфічні поля структурованого JSON-логу).
- **Можливі наслідки:** Регресія коду; повернення до заборонених синонімів з глосарію (`Modification`, `Transaction`); пропуск обов'язкових полів MDC.
- **Спосіб виявлення:** Поява згенерованого коду без обов'язкових анотацій чи логів; відхилення від глосарію.
- **Захід з попередження/пом'якшення:** Збереження ключових рішень у постійних артефактах репозиторію (`spec/SRS.md`, `spec/domain_glossary.md`); передача посилань на файли замість сподівання на контекстну пам'ять; використання інструменту читання файлів для перевірки контрактів.

### RSK-AI-05: Помилки під час роботи з інструментами (Tool Failures & Desync)
- **Прояв:** Неузгодженість стану локального Git-репозиторію з віддаленим GitHub, збої викликів GitHub MCP Server через конфлікти параметрів або мережеві помилки.
- **Можливі наслідки:** Втрата змін, несинхронізовані статуси задач, дублювання тікетів.
- **Спосіб виявлення:** Регулярний `git status`, аудит списку issues через GitHub API.
- **Захід з попередження/пом'якшення:** Фіксація кожного результату виклику MCP; верифікація згенерованого номера `#number` перед створенням залежних тікетів.

### RSK-AI-06: Недостатній людський контроль критичних рішень (Automation Bias / Rubber-Stamping)
- **Прояв:** Інженер сліпо покладається на висновки агента, затверджує пул-реквести або рішення Gate без глибокого вивчення коду, вважаючи, що "ШІ знає краще".
- **Можливі наслідки:** Пропуск критичних вразливостей безпеки, порушення ACID-інваріантів, втрата контролю над архітектурою.
- **Спосіб виявлення:** Аудит журналів рішень (`logs/plan-gate-decision.md`), наявність виявлених зауважень під час перевірок.
- **Захід з попередження/пом'якшення:** Формальне маркування контрольних точок міткою `role:human` з обов'язковим заповненням чек-листа аудиту та забороною автоматичного закриття тікетів агентом.

## 4. Детальний аналіз традиційних інженерних ризиків

### RSK-TR-01: Порушення властивості Append-Only журналу споживання
- **Прояв:** Випадкове додавання методів модифікації `PUT`/`DELETE` або оновлення записів через каскадні зв'язки JPA.
- **Наслідки:** Фальсифікація історії споживання, порушення закону незмінності дегустаційного щоденника.
- **Заходи контролю:** Тест `AppendOnlyImmutabilityAcceptanceTest` (BDD-SCN-005), відсутність методів оновлення в `ConsumptionRepository`, створення БД-тригера PostgreSQL:
  ```sql
  CREATE RULE no_update_consumption AS ON UPDATE TO consumption_entries DO INSTEAD NOTHING;
  CREATE RULE no_delete_consumption AS ON DELETE TO consumption_entries DO INSTEAD NOTHING;
  ```

### RSK-TR-02: Розрив реляційної цілісності при злитті (Merge Cascade Failure)
- **Прояв:** Неповна міграція пакувань або записів споживання від дубліката до цільового товару, зависання "битих" зовнішніх ключів.
- **Наслідки:** Помилки `Foreign Key Violation`, втрата історичного об'єму користувача.
- **Заходи контролю:** Ізольований тест `CatalogMergeIT` на Testcontainers з перевіркою Rollback при змодельованому винятку; обов'язкова анотація `@Transactional(isolation = Isolation.READ_COMMITTED)`.

### RSK-TR-03: Гонки даних (Race Conditions) при паралельному голосуванні
- **Прояв:** Одночасні запити від користувачів призводять до спотворення лічильників `confirm_votes` / `reject_votes` або подвійного зарахування голосу одного користувача.
- **Наслідки:** Некоректний перехід версії в статус `VERIFIED` або `REJECTED`.
- **Заходи контролю:** Накладення унікального індексу БД `CREATE UNIQUE INDEX idx_vote_user_ver ON version_votes (user_id, version_id);`, багатопотоковий тест `VersionVotingConcurrencyIT`.

### RSK-TR-04: Помилки розрахунку часових меж діб $[00:00, 24:00)$
- **Прояв:** Неправильна інтерпретація часового поясу користувача (обчислення за сервером UTC замість IANA-зони клієнта), втрата записів між `00:00:00.000` та `00:00:00.999`.
- **Наслідки:** Хибний розрив або неправомірне нарахування стріків (`Current Streak`).
- **Заходи контролю:** Параметризовані тести `StreakCalculationServiceTest` із тестуванням високосних років, переходу на літній/зимовий час та граничних точок `00:00:00.000`.
