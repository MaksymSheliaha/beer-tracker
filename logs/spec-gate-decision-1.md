## 1. Audit Criteria Evaluation

### 1.1. Несуперечність (Consistency)
* **Архітектурна суперечність у механізмі незмінності (Immutability vs. Tombstone Cascade):**
  * У розділі 2.3 (п. 2) та REQ-NF-010 зафіксовано: *«The database schema shall restrict UPDATE and DELETE permissions on the consumption_events table for application connection pools»* та *«The server provides no UPDATE or DELETE endpoints for committed consumption records»*.
  * Водночас у REQ-F-012 (AC-012.1) вимагається: *«When an Administrator deletes a product, all consumption events referencing that product shall have their product reference updated to the Tombstone ID»*.
  * Відсутнє архітектурне розв'язання того, як операція видалення виконує оновлення при заблокованих правах на `UPDATE`.
* **Помилка логіки переходів у діаграмі станів консенсусу (Розділ 4.2):**
  * Перехід `Voting_Edit --> Verified : Accumulates >= 5 Downvotes (Draft discarded, prior Verified remains)` спрямовує чернетку, що відхиляється, у стан `Verified`. Згідно з REQ-F-003 (AC-003.4), чернетка редагування повинна знищуватись, а не переходити у статус верифікованої.
* **Відсутність базової вимоги для життєвого циклу редагування:**
  * У розділах 1.2.1 (2), Таблиці 2.2 та Діаграмі 4.2 фігурує процес подання правок до існуючого продукту (`Draft_Edit`, скидання голосів при новому редагуванні). Проте у Розділі 3.1 повністю відсутня функціональна вимога на редагування існуючого продукту (присутня лише `REQ-F-001: New Product Registration`), а в Розділі 3.2.2 відсутній ендпоінт оновлення (`PUT/PATCH /api/v1/products/{id}`).

### 1.2. Тестованість (Testability)
* **REQ-F-007 (AC-007.2) — Недетермінованість масового онлайн-відновлення:**
  * Вимога стверджує: *«When network connectivity is restored, the client shall start the 60-second Soft-Undo timer for each queued event»*. Не визначено поведінку інтерфейсу та черги при великій кількості накопичених подій (паралельний чи послідовний запуск таймерів), а також поведінку при раптовому виході користувача під час зворотного відліку.
* **REQ-F-003 — Відсутність правила розв'язання гонитви (Race Condition):**
  * Відсутнє детерміноване правило пріоритету при одночасному досягненні 10 Upvotes та 5 Downvotes у паралельних транзакціях.
* **REQ-F-011 — Невизначеність Tie-Breaking для лідербордів:**
  * При однаковій кількості споживань та об'ємі відсутній вторинний критерій сортування, що унеможливлює створення стабільних автотестів.

### 1.3. Відсутність невизначених термінів (Glossary Compliance)
* **Порушення власних заборонених синонімів (Forbidden Synonyms) із Розділу 1.3:**
  * `Item` *(заборонено для BeerProduct)*: використано у визначеннях `Collection`, `Wishlist`, а також у `AC-005.1` та `AC-011.2`.
  * `Intake` *(заборонено для ConsumptionEvent)*: використано в заголовку Таблиці 2.2.
  * `Rollback` *(заборонено для SoftUndo)*: використано в описі Розділу 1.2.1 (п. 5) та заголовку сценарію `BDD-SCN-003`.
  * `Spam` *(заборонено для Untrusted)*: використано в Таблиці 2.2 та формулюванні `REQ-F-012`.
  * `Stars` *(заборонено для Rating)*: використано в Розділі 1.2.1 (п. 5), `AC-011.1` та `AC-011.2`.
* **Невизначені абревіатури в тексті:**
  * Скорочення `ABV`, `CAPTCHA`, `EAN-13`/`UPC` не описані у глосарії термінів.

### 1.4. Реалістичність критеріїв прийняття (Acceptance Criteria)
* **Пропущено граничні критерії для відгуків (REQ-F-009):**
  * Обмеження у $\le 2000$ символів не відображене у критеріях прийняття `AC-009.x` (відсутня перевірка валідації довжини та реакція бекенду на перевищення ліміту).
* **Відсутність вимог на ручне керування Wishlist:**
  * Відсутні функціональні вимоги та REST API для додавання або видалення позицій із `Wishlist` вручну без здійснення факту споживання.
* **REQ-F-010 — Відсутність AC для некоректної часової зони:**
  * Не описано поведінку сервера при передачі клієнтом невалідного рядка IANA (наприклад, відсутній код помилки HTTP 400).

## 2. Підсумковий вердикт

- **Виявлені дефекти:**
  1. CRITICAL: Архітектурна суперечність між жорсткою забороною `UPDATE` для таблиці `consumption_events` (REQ-NF-010) та каскадним оновленням зовнішніх ключів на `Tombstone` (REQ-F-012).
  2. CRITICAL: Помилка в схемі станів консенсусу (Розділ 4.2): перехід при 5 Downvotes скеровував чернетку в стан `Verified` замість її знищення.
  3. CRITICAL: Функціональна неповнота: відсутні вимоги та API-маршрути для процесу редагування продукту (Submit Edit Draft) та ручного керування `Wishlist`.
  4. MAJOR: Порушення правил Domain Glossary — використання термінів із списку *Forbidden Synonyms* (`item`, `intake`, `rollback`, `spam`, `stars`) у тексті специфікації та критеріях прийняття.
  5. MINOR: Відсутність граничних критеріїв прийняття для довжини коментаря (REQ-F-009), невалідних IANA таймзон (REQ-F-010), масового офлайн-відновлення (REQ-F-007) та правил tie-breaking (REQ-F-011).

- **Рішення:** **REJECTED**
