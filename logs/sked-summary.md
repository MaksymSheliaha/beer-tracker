# Підсумок SKED-сесії

## 1. Початковий задум
Автоматизація процесу фіксації обсягів спожитого пива та ведення особистої колекції відгуків на скуштовані напої. Система поєднує функції кількісного трекера та особистого дегустаційного щоденника.
Базові можливості:
* Кількісний трекінг споживання.
* Формування колекції.
* Оцінювання та написання відгуків.
* Аналіз бази відгуків та споживання.

---

## 2. Ключові виявлені невизначеності
* **Модель доступу та архітектура:** Не було визначено, чи система є суто локальним застосунком для одного користувача, чи багатокористувацькою клієнт-серверною системою зі спільною базою.
* **Життєвий цикл і зв'язок сутностей:** Було незрозуміло, чи відгук пишеться на кожен факт споживання, чи закріплюється один раз за продуктом; як продукт потрапляє в персональну колекцію та взаємодіє з вішлістом (включно з ручним додаванням/видаленням з вішліста).
* **Джерело даних каталогу та консенсус:** Не було визначено, звідки надходять дані про пиво (зовнішні бази, сканування штрих-кодів чи краудсорсинг користувачами за wiki-принципом), а також життєвий цикл подання правок (`Draft_Edit`) та розв'язання гонитви (Race Conditions) між 10-м Upvote і 5-м Downvote.
* **Офлайн-режим та незмінність історії:** Не була формалізована поведінка системи за відсутності мережі, а також межі дозволеного редагування/скасування записів споживання заднім числом і черговість відправки при відновленні з'єднання.
* **Глибина та метрики аналітики:** Було не визначено, чи розраховуються показники впливу на здоров'я/етанол/проміле (BAC), чи трекінг ведеться суто у фізичних об'ємах; як враховувати часові пояси користувача для розрахунку діб та серій (streaks), поведінка при невалідній таймзоні та вторинне сортування (tie-breaking) для лідербордів.
* **Безпека краудсорсингу та приватність:** Були відсутні механізми захисту від створення бот-акаунтів (Sybil-атак) для спаму неіснуючими продуктами чи накрутки голосів, а також не було визначено статус публічності автора нового продукту.
* **Архітектурний парадокс незмінності:** Виник конфлікт між забороною SQL `UPDATE` для таблиці споживань та вимогою підміни зовнішнього ключа на `Tombstone` при адміністративному видаленні продукту.

## 3. Відхилені / Скориговані припущення агента
* **Припущення моделі:** Розраховувати спожитий чистий етанол (г), одиниці алкоголю або проміле (BAC) на основі ABV напою та інтегрувати аналітику зі сторонніми сервісами здоров'я (Apple Health / Google Health Connect).  
  **Рішення людини:** Відхилено. Жодних медичних розрахунків чи сторонніх інтеграцій. Система фіксує виключно фізичний об'єм спожитого продукту в літрах (L).
* **Припущення моделі:** Дозволити довільне або довготривале серверне редагування/скасування записів споживання (наприклад, вікно Undo у 10–15 хвилин на сервері).  
  **Рішення людини:** Скориговано. Журнал споживання на сервері є суворо незмінним (immutable). Скасування (Soft-Undo) реалізується виключно на стороні клієнта за 60-секундним таймером для онлайн-записів.
* **Припущення моделі:** Запускати новий 60-секундний Soft-Undo таймер для кожного запису з офлайн-черги після появи мережі.  
  **Рішення людини:** Скориговано. Оскільки користувач уже мав необмежений час скасувати записи локально під час перебування в офлайні, при відновленні мережі черга відправляється на сервер негайно за чергою FIFO без додаткового очікування.
* **Припущення моделі:** Дозволити стандартному застосунку виконувати `UPDATE` у таблиці `consumption_events` під час видалення продукту.  
  **Рішення людини:** Скориговано. Стандартний пул з'єднань застосунку має строго `INSERT` та `SELECT` (операції `UPDATE` та `DELETE` заборонені). Адміністративне переприв'язування зовнішніх ключів на Tombstone виконується виключно через збережену процедуру з підвищеними привілеями (`SECURITY DEFINER`).
* **Припущення моделі:** Інтегруватися із зовнішніми каталогами та API штрих-кодів (Untappd, RateBeer, Open Food Facts).  
  **Рішення людини:** Відхилено. Зовнішніх баз немає; каталог формується самими користувачами за wiki-принципом із консенсусним підтвердженням спільнотою (10 Upvotes для верифікації, 5 Downvotes для відхилення). При конкурентних запитах діє принцип First-Commit Wins із песимістичним блокуванням рядка (`SELECT FOR UPDATE`).
* **Припущення моделі:** Повністю видаляти з бази непідтверджені нові продукти у разі перевищення порогу голосів "Reject".  
  **Рішення людини:** Скориговано. Відхилений новий продукт не видаляється фізично (щоб не зламати історію тим, хто вже зафіксував його споживання), але переводиться у статус `Untrusted` і приховується з глобального пошуку. Якщо ж відхиляється чернетка редагування існуючого продукту (`Draft_Edit`), вона знищується, а чинною залишається попередня верифікована версія.
* **Припущення моделі:** Публічно відображати автора, що створив або відредагував продукт у каталозі.  
  **Рішення людини:** Відхилено / Скориговано. Інформація про автора фіксується виключно у внутрішньому аудит-журналі для безпеки й адміністрування, але є суворо конфіденційною і ніколи не видається в публічні DTO.
* **Припущення моделі:** Формувати топи споживання (улюблені продукти, пивоварні, стилі) на основі середнього рейтингу користувача.  
  **Рішення людини:** Скориговано. Аналітичні топи формуються виключно на основі кількості/частоти фактів споживання та об'єму. У разі однакових значень tie-breaking здійснюється суто за датою останнього споживання (`last_consumed_at DESC`).
* **Припущення моделі:** Дозволити відгуки на неспожите пиво або довільну довжину коментаря.  
  **Рішення людини:** Відхилено. Оцінити та написати відгук (1.0–5.0, крок 0.5, коментар $\le 2000$ знаків) можна тільки на напій, що є в особистій Колекції.

## 4. Прийняті архітектурні обмеження
* **Клієнт-серверна модель:** Сервер є єдиним джерелом правди (Single Source of Truth) для всіх сутностей. Взаємодія здійснюється суворо через REST API з шифруванням TLS 1.3 поверх HTTPS.
* **Append-Only Immutability та SECURITY DEFINER:** Журнал подій споживання (`consumption_events`) є суворо незмінним для звичайних користувачів і сервісів. Заміна зовнішніх ключів на системний `Tombstone` (`[Deleted / Unknown Product]`) при адмін-видаленні реалізована через ізольовану процедуру `SECURITY DEFINER`.
* **Нормалізація часових поясів (UTC-to-Local) та сувора валідація:** Усі часові мітки зберігаються в UTC. Клієнт передає свій IANA-часовий пояс; у разі передачі невалідного ідентифікатора сервер повертає `HTTP 400 Bad Request`.
* **Двоверсійна модель каталогу (Dual-Version Concurrency):** Продукт у каталозі підтримує рівно 1 активну `VerifiedVersion` та не більше 1 поточної `DraftVersion`. Подання нових правок здійснюється через `PUT /api/v1/products/{id}/draft` і скидає лічильники голосів.
* **Офлайн-буферизація та миттєва синхронізація:** 60-секундний Soft-Undo активний лише для онлайнових дій. В офлайні події пишуться в локальне сховище (IndexedDB/SQLite) і відправляються на сервер негайно після появи зв'язку.
* **Захист від Sybil-атак та ботів:** Лімітування створення акаунтів (до 5 з однієї IP на годину), обов'язкова CAPTCHA. Поріг зрілості (`AccountMaturity`): вік $\ge 48$ годин та наявність $\ge 1$ підтвердженого споживання для додавання/редагування продуктів та голосування в консенсусі. Денний ліміт — не більше 5 нових продуктів на добу.
* **Повнота API життєвого циклу:** Додано окремі ендпоінти для ручного додавання/видалення продуктів із Вішліста (`POST` / `DELETE /api/v1/users/me/wishlist`), а також валідацію текстових коментарів відгуків ($\le 2000$ символів).
