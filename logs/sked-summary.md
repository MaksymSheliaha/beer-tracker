# Підсумок SKED-сесії

## 1. Початковий задум
Автоматизація процесу фіксації об'ємів спожитого пива та ведення персональної колекції відгуків на продегустовані напої. Система поєднує в собі функції кількісного трекера та особистого дегустаційного щоденника. Межа проектованої системи на поточному етапі — серверна частина (Backend REST API).

## 2. Ключові виявлені невизначеності
- **Зв'язність кількісного та якісного обліку:** Було не визначено, чи факт вживання є єдиною сутністю з дегустаційним відгуком, чи вони мають незалежні життєві цикли.
- **Модель власності каталогу та модерація:** Не було зафіксовано, чи є каталог пива загальним (shared wiki) чи персональним для кожного користувача, а також були відсутні правила вирішення конфліктів та верифікації правок спільноти.
- **Цілісність даних при видаленні та злитті товарів:** Було незрозуміло, що відбувається з незмінними записами споживання користувачів при видаленні товару або об'єднанні дублікатів модератором.
- **Правила консенсусу крауд-модерації:** Не було визначено точні порогові значення підтверджень/відхилень для автоматичної зміни статусів запропонованих користувачами версій.
- **Часові пояси та межі календарного дня:** Відсутність правил визначення зміни доби для нічного споживання та розрахунку неперервних стріків споживання.
- **Модель обліку тари та об'ємів:** Було невизначено, чи об'єм вказується довільно, чи прив'язаний до типів упаковки (пляшка, банка, кег) та розливного пива.

## 3. Відхилені / Скориговані припущення агента
- **Припущення моделі:** Об'єм споживання вказується як довільне скалярне число в мілілітрах без структуризації за тарою.  
  **Рішення людини:** Скориговано. Сутність "Пиво" обов'язково містить перелік доступних пакувань (`Packaging`: об'єм у мл, тип тари, штрих-код). Запис споживання фіксує ідентифікатор пакування та кількість спожитих одиниць (наприклад, 2 банки по 500 мл), а розливне пиво враховується як окремий товар каталогу.
- **Припущення моделі:** При видаленні товару модератором використовується стандартний Soft Delete, і повні атрибути товару залишаються видимими в старих звітах.  
  **Рішення людини:** Скориговано. Видалений продукт замінюється системним плейсхолдером ("Видалений продукт") без властивостей. У користувача зберігається факт, дата та літраж споживання, але без детальної інформації про видалений товар.
- **Припущення моделі:** Для краудсорсингової верифікації версій застосовується поріг `(Upvotes - Downvotes) >= 3`.  
  **Рішення людини:** Скориговано. Поріг для автоматичного підтвердження або видалення — строго 5 голосів одного типу ($N=5$). Автор версії не має права голосувати. Якщо модифікація набирає 5 реджектів — вона видаляється (залишається діюча версія); якщо абсолютно новий товар набирає 5 реджектів — він отримує статус `Rejected` і виноситься в чергу модератора.
- **Припущення моделі:** Дозволити ретроспективне редагування та коригування логів споживання користувачем.  
  **Рішення людини:** Відхилено. Журнал споживання є строго Append-Only: будь-яка модифікація чи видалення зафіксованих записів заборонені.
- **Припущення моделі:** Інтеграція із зовнішніми базами даних та відкритими API пива для автозаповнення.  
  **Рішення людини:** Відхилено. Жодних сторонніх API. База ведеться виключно силами користувачів системи за принципом wiki.

## 4. Прийняті архітектурні обмеження
- **Архітектурний стиль:** Робота виключно через headless REST API за стандартом JSON. UI, комп'ютерний зір (OCR) для етикеток та токсикологічні розрахунки (BAC) повністю винесені за межі системи (Out-of-Scope).
- **Append-Only журнал:** Повна заборона методів `PUT`, `PATCH`, `DELETE` для сутності `ConsumptionEntry` на рівні API та бази даних.
- **Правило єдиного відгуку:** Користувач може мати щонайбільше один відгук та одну оцінку (1.0–5.0) на продукт, які дозволено створювати тільки після наявності факту споживання.
- **Превентивна дедуплікація:** API блокує створення товарів-дублікатів (HTTP 409 Conflict) за збігом нормалізованої пари `(brewery + name)` або асоційованих штрих-кодів.
- **Автоматична синхронізація Wishlist та Collection:** Факт першого вживання товару автоматично переносить його в `Collection` і видаляє зі списку бажань `Wishlist` у межах однієї транзакції.
- **Злиття дублікатів (Merge):** Модератор має право виконати злиття дублікатів, переприв'язуючи історію споживання та залишаючи новіший відгук користувача.
- **Часові пояси та зміна доби:** Розрахунок добової аналітики та стріків споживання здійснюється за збереженим IANA-часовим поясом користувача; нова доба настає рівно о `00:00:01`.
